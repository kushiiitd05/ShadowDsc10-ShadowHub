\section{Problem, data and the fixed split}

\begin{figure*}[t]
\centering\includegraphics[width=0.94\linewidth]{\FIG fig_pipeline.pdf}
\caption{\textsf{PIPELINE.} One feature pipeline, two tracks. Track A answers the course rubric with $x^\ast$ = LightGBM
\code{cs02} on a fixed split. Track B is the forecaster we submit; it is improved on rolling development folds and frozen.
Track B is not coreset-ed (box in Section~1).}
\end{figure*}

\textbf{Task.} Forecast the daily order volume of each of 1{,}115 retail hubs for the next 42 days. One row is one hub on one
day. The response is skewed (median about 6{,}000 on open days, 0 on closed days), so every model is fitted on
$\log(1+y)$ and scored by RMSLE $=\sqrt{\tfrac1N\sum(\log(1+\hat y)-\log(1+y))^2}$; RMSE on the log scale and $R^2$ on the
log scale are reported beside it, as the end-term brief asks.

\begin{stamp}{Reading guide: two tracks, three model names}
\textbf{Track A, the rubric (Sections 2--5).} $x^\ast$ = LightGBM recipe \code{cs02} (63 leaves, feature fraction 0.2, row
bagging), trained on the fixed split; ridge is the second model; every summary is fitted with the same settings.
\textbf{Track B, the forecaster we submit (Sections 6--7).} \code{hp17} (the same LightGBM, tuned: 255 leaves, feature
fraction 0.15, strong L2), 3 seeds, blended 0.8/0.2 in log space with TabPFN-TS (365- and 730-day contexts, 0.10 each). It
writes the forecast file for the unlabelled window from 20 Jun 2015, so it has development-fold scores only.
\textbf{Why Track B is not coreset-ed.} TabPFN-TS is a pretrained model that reads each hub's history at prediction time:
it has no training loss $F$, no fitted $x^\ast$ and no rows to weight, so sensitivities are not defined for it; and the rubric's
same-model rule would need the whole blend refitted for 5 repeats $\times$ 7 sizes $\times$ 3 methods.
\end{stamp}

\textbf{Rows and columns.} Each training row is a (forecast origin, hub, target day) triple: for an origin $o$ the features
are built from history up to $o$ only, and the label is the volume on day $o+h$, $h=1..42$. We build 37 origins two weeks
apart (label windows end by 19 Jun 2015) with \n{342} engineered columns: calendar, promotion and holiday flags known in
advance, hub metadata, rolling medians over 7--365 days, same-weekday means, a cross-fitted hub target encoding, and data-gap
flags. The end-term training split has \n{1,133,640} open rows with positive volume; $1{,}133{,}640\times342=\n{387.7}$
million cells, far above the 3-million floor of the course.

\textbf{Split (fixed once, before any end-term run).} Train = every origin whose 42-day label window ends on or before
8 May 2015; test = the last 42 training days, 9 May -- 19 Jun 2015 (\n{46,830} rows = 1{,}115 hubs $\times$ 42 days).
Hyper-parameters of the full model $x^\ast$ are set on a training-only holdout and then frozen. Closed days are \emph{kept}
in the test set with prediction 0 (their error is 0); this inflates $R^2$, so RMSLE without the open-but-zero rows is also
reported.

\textbf{Data preparation carried over from the midterm, and what changed for forecasting.} The midterm cleaned the raw file
(dates parsed, 180 hubs with a six-month gap in 2014 flagged, open days with zero volume flagged, weekday checked against
the date). For forecasting we added four rules, each because a check failed without it:
\begin{itemize}
\item \emph{Features stop at the origin.} Every rolling statistic for origin $o$ is computed from days $\le o$; a test asserts
  that no history date exceeds the origin. Without it a 7-day median would read the first forecast days.
\item \emph{Training-origin purge.} An origin is used for training only if its whole 42-day label window ends on or before the
  forecast origin; otherwise a training label would sit inside the evaluated window.
\item \emph{Cross-fitted hub encoding.} The hub's mean log volume is a strong feature, but computed on the same rows it is fitted
  on it leaks the label; scikit-learn's \code{TargetEncoder.fit\_transform} uses internal cross-fitting, and the earlier
  \code{fit().transform()} pattern (which does not) was replaced.
\item \emph{Fixed rounds.} Early stopping on the evaluated fold leaks; the final setting uses 1000 rounds at learning rate
  0.025, fixed before scoring.
\end{itemize}

\begin{limit}{Overlap with model selection, and the check we ran}
The end-term test window is the same 42 days as development fold~4, whose scores were part of earlier recipe decisions
(\code{cs02} over \code{base}; the forecaster's gate and weight). No fold-4 label enters any end-term fit, sampling
probability, column choice, number of rounds or ridge $\lambda$. To test whether the overlap mattered we re-took every decision
with fold~4 removed (\code{code/leakage\_check.py}, table below): \textbf{none changes}. The absolute test RMSLE is still a
development-fold number, not an untouched holdout; the coreset-versus-uniform comparison is unaffected, because both use the
identical model and settings.
\end{limit}

\section{The full model \texorpdfstring{$x^\ast$}{x*} and a second model}

\textbf{Why LightGBM.} Volume depends on interactions (weekday $\times$ promotion $\times$ hub format, holiday
proximity, data gaps) that a tree ensemble captures without hand-made products, and LightGBM handles 1.1M rows $\times$ 342
columns in about a minute. Recipe (\code{cs02}): 63 leaves, feature fraction 0.2, row bagging 0.85 every iteration,
min child 80, learning rate 0.05, \n{1184} rounds fixed from the training-only holdout. \textbf{Why ridge as the second
model.} It is the model for which coreset theory is exact (squared loss, closed form), so it shows what the theory
predicts; $\lambda=0.1$ was chosen on the same holdout. Both models are trained with identical settings on the full data
and on every summary.

\textbf{Why these features.} Every column is known at the forecast origin: history up to the origin, and the calendar,

\section{Sampling: rows (Plot 1) and columns}

\textbf{Methods.} (i) \emph{Uniform}: $m$ rows with replacement, weight $n/m$ each (the baseline on every plot).
(ii) \emph{Hub-stratified}: equal rows per hub (added because the smallest size, 2{,}000, is close to the hub count).

each size is repeated 5 times with new seeds for sampling, rough models and training; we plot the median and the min--max band.

\section{The coreset (Plots 3--5)}

\textbf{Rough models.} Five models $\tilde x_1..\tilde x_5$ fitted on 20k-row uniform samples with different seeds. Their
roughness is $\alpha_t=F(P,w,\tilde x_t)/\text{opt}$ with opt $=F(P,w,x^\ast)$; the largest is \n{2.45} for LightGBM and
\n{1.01} for ridge (a 20k-row ridge is already almost optimal).

\textbf{Sensitivities.} With $f_i$ the squared log error of row $i$ and $F_\text{sum}(\tilde x_t)=\sum_j w_jf_j(\tilde x_t)$,
\begin{eqbox}
\[ s_i=\max_{t=1..5}\Big[\frac{f_i(\tilde x_t)}{F_\text{sum}(\tilde x_t)}+\frac1n\Big], \]
\[ S=\sum_{i=1}^n s_i,\qquad p_i=s_i/S,\qquad w_i=\frac{1}{m\,p_i}. \]
\end{eqbox}
Using the sum (not the mean) in the denominator makes $\sum_i f_i/F=1$ per rough model, so $S$ must lie in $[2,6]$ for five
models and one group; a unit test enforces it. Measured: $S=\n{2.47}$ (LightGBM), \n{2.12} (ridge). The rough models score
every training row; no test row is ever scored by them. For trees there is no $(1\pm\varepsilon)$ guarantee; we call the method
\emph{heuristic sensitivity-motivated importance sampling}.

\textbf{Why it should help here.} A row's sensitivity is large when some rough model fits it badly: event days, hubs after a
data gap, sharp promotion jumps. Uniform sampling sees such rows in proportion to their count (a few per cent), while the
coreset over-samples them and down-weights them by $1/(mp_i)$, so the weighted loss stays an unbiased estimate of the full
loss but with lower variance on exactly the rows that drive the error. The $1/n$ term keeps every row reachable, which bounds
the largest weight. The histogram below shows the mass is spread over three orders of magnitude, with a thin tail of rows
up to about 250 times the uniform share $1/n$.

\begin{figure}[h]
\centering\includegraphics[width=\linewidth]{\FIG fig_hist_sensitivity.png}
\caption{\textsf{SENSITIVITY SCORES} $s_i/S$ over all \n{1,133,640} training rows (log axes). The floor at
$10^{-6.4}\approx1/(nS)$ is the $1/n$ term; the tail is what the coreset over-samples.}

\section{Track B, the forecaster we submit: what we tried, what failed and why}

Separately from the coreset study we improved the forecaster whose output is the submission file. It starts from the same
LightGBM recipe as $x^\ast$; the coreset study keeps \code{cs02} as $x^\ast$ (reading guide, Section~1). Evaluation uses
rolling forecast origins: development folds 1--4 start on 2 Jan, 13 Feb, 27 Mar and 8 May 2015 (46{,}830 rows each); fold 5
starts on 19 Jun 2014 and is season-matched to the real forecast window, which also has no regional holidays.

\begin{eqbox}\small\textbf{Adoption gate, fixed before the runs.} A change is adopted only if (a) its mean gain over
the baseline on folds 2--4 is $\ge\n{0.0024}$, twice the measured seed-to-seed noise \n{0.0012}; (b) at least 2 of the 3
folds improve; (c) the sign is the same for seeds 20260807/08/09; (d) it still holds without open-but-zero rows; (e) fold 5
is checked. Better on most folds but missing the gate = \emph{challenger}, not adopted.
\end{eqbox}

\textbf{What worked, and why.} \emph{Feature fraction 0.2 with bagging} ($0.1312\to0.1190$): with 342 correlated
columns (many rolling windows of the same series), each tree sees a small random subset, which decorrelates the trees and
stops a few long-window medians from dominating. \emph{Seed averaging} (\n{-0.0017}): free variance reduction.
\emph{\code{hp17}} (255 leaves, min child 160, L2 24.1, feature fraction 0.15): bigger trees with strong shrinkage of leaf
values fit hub-specific weekday and promotion patterns without over-fitting small hubs. \emph{TabPFN-TS}: a pretrained
tabular foundation model run per hub on its own history; its errors are different from the trees' (it reads each series'
recent level directly), so a 20\% log-space blend helps.

(\code{code/freeze\_audit.py}), not taken from the run logs. Candidate formula, for hub $h$ and day $t$

\begin{eqbox}\small
\[ L_{h,t}=0.8\cdot\tfrac13\!\!\sum_{s\in\{07,08,09\}}\!\!\ell\big(\hat y^{\,\text{hp17}}_{s}\big) \]

\[ \hat y_{h,t}=\max\big(0,\;e^{L_{h,t}}-1\big)\ \text{if open, else }0. \]

\section{Limitations and open items}

\begin{itemize}
\item \textbf{Timing.} Development timings only; exclusive rerun pending (Section~4).
\item \textbf{Fold 4 = test window.} No decision changes without it (Section~1), but the test RMSLE of $x^\ast$ is not from an
  untouched holdout; no labelled window was left unused.
\item \textbf{Winter.} The frozen model is \n{0.0027} worse than \code{hp17} alone on fold~1 (winter, year-end); the forecast
  window is summer and fold~5 improves, so we accept it, but it is unexplained.
\item \textbf{Trees.} The coreset has no guarantee for trees; its advantage at mid sizes is empirical (5 repeats, 1 split). A
  check with unnormalised weights at one size was planned and not run.
\item \textbf{Columns.} Gaussian/CountSketch projections for ridge were not run; only the column-selection experiment for trees.
\item \textbf{Fold 5} covers 935 of 1{,}115 hubs (180 hubs lack 2014 H2 data); its error is larger because of 9 open-zero rows.
\item \textbf{Closed rows} inflate $R^2$; read RMSLE first.
\end{itemize}

\section{Conclusion}

\textbf{Chosen summary size: $m=50{,}000$ rows with the sensitivity coreset.} There the LightGBM test RMSLE rises from
\n{0.1022} to \n{0.1070} (\n{+0.0048}), RMSE on the log scale is the same number, and $R^2$ stays above \n{0.998}; end-to-end
time falls from \n{59.7} s to \n{21.6} s (\n{2.75$\times$}). Uniform sampling at the same size is faster (\n{5.18$\times$}) but
\n{0.0032} worse, and needs two to four times as many rows to match. For ridge, sampling saves no time and changes nothing:
the build costs more than the full fit. Separately, the forecaster we submit (\code{hp17} + TabPFN-TS, 0.8/0.2 in log space)
improves on the \code{cs02} recipe by \n{0.0045} RMSLE on development folds 2--4, passed a gate fixed in advance (also with
fold~4 removed), and was frozen with hashes, sanity checks and a fallback; its forecast window has no labels, so it has no
test score.
